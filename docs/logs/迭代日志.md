## 阶段 0 · 需求分析与先决判断

**输入**：用户需求文档（基础必备 + 高阶功能），未上传参考材料。

**关键判断**：这个需求里有 4 个真正决定架构的难点，其余都是工程量。

| 难点               | 判断                                          |
| ---------------- | ------------------------------------------- |
| 浏览器里把 C 编译成 .hex | **不可能**在纯前端做。8051 的 C 编译器只有 SDCC 成熟，必须服务端调用 |
| 8051 指令级仿真       | 现成 JS 方案都不完整（无定时器/中断），需要自研                  |
| 原理图 + 精确引脚 + 网表  | 需要自研 SVG 编辑器 + 并查集网表                        |
| 连接真实硬件           | 浏览器唯一通道是 Web Serial，需 HTTPS                 |

**结论**：架构定为"零依赖 Node 服务端 + 纯前端仿真"，仿真全部在浏览器跑，  
服务端只做编译/鉴权/统计——这样 100 人并发仿真时服务端几乎无负载。

## 阶段 1 · 技术调研（材料已存 `docs/research/`）

### 1.1 编译器：确认只有 SDCC 一条路

调研结论：

- 不存在可用的纯 JS 8051 C 编译器（现存都是玩具级子集）；
- SDCC 是唯一活跃、支持 `<stdio.h>`/`<string.h>`、能直接出 Intel HEX 的方案。

实际验证（见 `docs/research/00-调研总览.md` §2）：

```
下载 sdcc-4.6.0-x64-setup.exe（9.9 MB，NSIS 安装包）
7-Zip 直接解压 → 3909 个文件 / 279 MB，无需管理员权限安装
sdcc -mmcs51 --model-small --stack-auto → 成功产出 .hex
```

**这一步同时发现了一个后续会反复出问题的地方**：SDCC 依赖 `cc1` 在 PATH 里，  
所以调用时必须把 `bin` 目录加进 PATH，否则 `cannot execute 'cc1'`。

### 1.2 仿真内核：决定自研，并找到黄金参照

对比过 `js51`、`8051sim`、`emu8051-stc`，都不满足（详见架构文档第一节）。

**关键发现**：SDCC 自带 `ucsim_51.exe`——一个指令级 8051 模拟器。  
它就是我的"标准答案"。有了它，自研内核就有了客观的验收标准，  
而不是"我觉得对"。

### 1.3 真实硬件：找到可移植的协议描述

`raw.githubusercontent.com` 不可达，改用 `cdn.jsdelivr.net/gh` 拿到 stcgal 的  
`protocols.py`，逆推出 STC89 ISP 的完整帧格式与命令序列（已存 `docs/research/`）。  
这决定了"连接真实硬件"从"可能做不了"变成"协议层可做"。

### 1.4 环境事实（已验证）

```
node 22.22.2 → node:sqlite 可用（DatabaseSnapshot/StatementSync）
              → 不需要 better-sqlite3，避免原生编译
7-Zip 26.03 → 可解压 NSIS 安装包
```

## 阶段 3 · 8051 内核 + 与 ucsim_51 对拍

先写内核，再用 ucsim 做黄金参照。这个过程**抓到了 4 个真 bug**：

| 缺陷                | 症状                   | 根因                                                                        | 修复                              |
| ----------------- | -------------------- | ------------------------------------------------------------------------- | ------------------------------- |
| RET 字节序           | 子程序返回跳到 0x5400 之类乱地址 | 8051 压栈先 PCL 后 PCH，且 **SP 先自增再存**；弹栈必须先弹 PCH                              | 重写 `pushStack/popStack/popPC`   |
| TCON 掩码           | 定时器永不启动              | 可写位是 bit0/2/4/6（IT0/IT1/TR0/TR1）→ 掩码 `0x55`；早期写成 `0x0F` 把 TR0/TR1 挡掉      | 改 `(v & 0x55)` + `(old & 0xAA)` |
| `softReset`       | 复位后程序被擦光             | `reset()` 会 `code.fill(0)`，先存引用再 reset 等于擦的是同一块内存                         | 改成 `code.slice()` 副本            |
| `runCycles` 外设不前进 | 定时器/串口不走             | `step()` 内部已调用 `tick()`，`runCycles` 只调 `step` 是对的；而我早期在外部又调 `tick`，导致时间翻倍 | 统一约定：**step() 已含 tick()**       |

### 对拍结果

```
arith_logic   PC=0xDA ACC=0x38 PSW=0x41 SP=0x0B clks=60600   ✅ 完全一致
bitops        PC=0xDA ACC=0xFF PSW=0x40 SP=0x0A clks=67440   ✅
int_bit       PC=0xFB ACC=0xFF PSW=0xC0 SP=0x13 clks=42564   ✅
stack_call    PC=0x136 ACC=0x5F PSW=0x00 SP=0x0C clks=61524  ✅
uart_tx       PC=0xC4 ACC=0x05 PSW=0x00 SP=0x0A clks=68604   ✅
timer0_irq    寄存器全一致，PC/周期差 1 个机器周期            ✅（相位容许）
```

5/6 逐字节一致，1 个差 1 个机器周期（中断采样相位）。这个结果让我对内核有信心。

> 工程细节：本开发环境禁止 Node 派生子进程（`spawn` 返回 EBUSY），  
> 所以"调 SDCC/ucsim"这一步放在 `tools/make_oracle_fixtures.sh`（bash）里做，  
> 测试只读 fixture。这不是设计缺陷，是**环境适配**——服务端本身能正常 spawn。

## 阶段 4 · 原理图与器件仿真

### 4.1 电平穿透（蜂鸣器实验暴露的问题）

预设电路 `P1.0 ——1kΩ—— 三极管基极`，仿真里蜂鸣器**完全不响**。

根因：`netLevel()` 只认"直连 CPU 引脚 / 直连电源地"，基极网络两者都没有，  
被判成"悬空 = 高"→ 三极管恒导通 → 无通断。

修复：沿电阻/电感/排阻做**深度受限（≤4）的电平穿透**，用 `_passivePeers()`  
处理排阻（COM 与每个 Rn 配对）。

### 4.2 边沿敏感器件被漏采样（LCD1602 全空）

LCD1602 的 DDRAM 一直是空的，但"显示已开启"。

根因：器件状态每 **18 个机器周期**刷新一次，而 `LCD_E=1; LCD_E=0;` 的选通脉冲  
只有 **1–2 个机器周期**——采样必然落在脉冲之外。

修复：`CircuitSim` 挂到 `cpu.onPinChange`，对 LCD / 74HC595 做到"引脚一变就响应"；  
电平型器件（LED、数码管）仍走周期刷新，保证性能。

### 4.3 无源蜂鸣器计频错误

`simBuzzer` 只盯 `+` 脚计边沿，而 `+` 脚接 VCC 恒定不变 → 永远是 0 次翻转。  
修复：同时观察两端，任一端变化即记一次半周期。

### 4.4 数码管"扫描"语义

`active[]` 是"视觉保持"（人眼看到 4 位都亮），不是"当前被驱动"。  
测试里断言"同时亮 ≤2 位"因而失败。  
修复：新增瞬时值 `selected[]`（以及 `scanGapCycles` 记录扫描周期），  
把"视觉暂留"和"当前驱动"分开表达——这本身也是个好教学点。

## 阶段 5 · 15 个实验：从"编译不过"到"行为正确"

### 5.1 编译层：Keil 写法与 SDCC 的差异

10 个实验编译失败，错误分三类：

1. `intrins.h: No such file` —— SDCC **不提供**这个 Keil 头文件。  
   → 平台自带 `platform/include/intrins.h`，并在编译命令里永远加 `-I`。
2. `syntax error at 'sbit'` —— Keil 的位定义。  
   → 实现 Keil→SDCC 翻译：`sbit LED = P1^3;` → `__sbit __at (0x93) LED;`
3. `syntax error at 'code'` —— Keil 的代码存储区关键字。  
   → `unsigned char code x[]` → `__code unsigned char x[]`

**这里踩了一个数学坑**：位地址是 `SFR字节地址 + 位号`（P2=0xA0 → P2^5=0xA5），  
不是 `SFR×8 + 位号`（那是 0x20–0x2F 内部 RAM 位区的算法）。  
写成后者得到 0x505，汇编器报 `Page 0 Address Error`。

### 5.2 延时被编译器整个删掉

流水灯的 LED 不流动（或快到看不见）。  
反汇编发现：`delay_ms(200);` **一行代码都没生成**。

根因：`for(i=0;i<ms;i++) for(j=0;j<120;j++);` 里的 `i/j` 没有副作用，  
SDCC 的优化器把整个空循环删了。  
修复：`volatile unsigned int i, j;`，并在注释里写清"volatile 必不可少"。  
这本身就是一个很好的教学点，已写进起始代码注释。

### 5.3 `BEEP = ~BEEP` 在 SDCC 下恒为真

音乐播放实验只响一次。根因：Keil 里 `~` 对 `bit` 是按 1 位取反；  
SDCC 里 `__sbit` 经 `~` 提升为 `int`，`~0 = -1`、`~1 = -2`，赋回 bit 时"非零即真"→ 恒为 1。  
修复：`BEEP = !BEEP;`。这条差异值得写进教材对比表。

### 5.4 软件延时标定（发现时间记账翻倍）

为了让"延时 100 ms"真的等于 100 ms，写了 `tools/calibrate_delay.mjs`：  
编译→执行→量周期→反推循环常数。

**第一次标定得到 inner=13**，但随后用 ucsim 对拍思路复核时发现：  
标定脚本里写的是 `cpu.step(); cpu.tick(c);`，而 `step()` **内部已经 tick 过**，  
时间被记了两倍 → 标定值只有真实值的一半 → 所有延时快一倍。

修正为只调 `step()` 后重新标定：`inner = 28` → 916 周期/ms（误差 0.6%）。  
实测流水灯每步 **198.8 ms**（目标 200 ms）。

> 教训：**测量脚本本身也要被测**。如果只看到"数字看起来合理"就收工，  
> 这个 2 倍误差会一直藏着，直到学生算刷新率时对不上。

### 5.5 最终实验验证结果

15 个实验、55 项行为断言全通过，且不只验证"能跑"，而是验证"现象对不对"：

## 阶段 6 · 服务端

### 6.1 致命的一个字符：`-mcs51` vs `-mmcs51`

编译报 `error 131: cannot generate code for target 'cs51'`。

根因：SDCC 的端口选项是 `-m` + **端口名**，8051 的端口名是 `mcs51`，  
所以必须写 **`-mmcs51`**（两个 m）。写成 `-mcs51` 会被解析成"目标 = cs51"。

### 6.2 可用性探测永远失败

启动横幅一直显示"SDCC 存在但不可用：spawn --version ENOENT"。

根因：`probe()` 调用 `run(['--version'])`，而 `run(args)` 约定 `args[0]` 是**可执行文件**，  
结果 spawn 了一个叫 `--version` 的程序。  
修复：`run([path.join(binDir,'sdcc.exe'), '--version'])`。

> 这个 bug 很隐蔽：编译功能其实是好的（编译走的是另一条路径），  
> 只有"状态徽标"一直是红的。如果没有去看那一行日志，就会误判工具链不可用。

### 6.3 printf 死锁与链接失败（两个独立的坑）

**坑 1：死锁。**

```c
int putchar(int c){ while(!(SCON&0x02)); SBUF=c; ... }  // 复位后 TI=0，永远等不到
```

修复：首次直接写 SBUF，之后才等上一字节的 TI。

**坑 2：`Undefined Global _putchar`。**  
注入的 stub 放在文件最前面（早于 `#include <stdio.h>`）时，SDCC 不把它生成为  
`.globl` 符号，链接 `vprintf` 时报未定义，程序跳飞、串口一个字都没有。  
修复：**插到用户最后一个 `#include` 之后**。验证：`printf("OK %d",42)` → TX 收到 `OK 42`。

### 6.4 离线助教的变量名笔误

`const { findings, hardware } = analyze()` 后面用的是 `hw` → `ReferenceError: hw is not defined`  
→ 学生一提问就 500。  
修复：解构时重命名 `hardware: hw`。

### 6.5 学生注册语义

教师导入名单时已按"学号=账号"预建了学生账号，学生再来"注册"会 409。  
但需求是"教师导入后学生能注册使用"，所以正确语义是**认领/激活**：  
学号匹配就允许设置自己的密码并登录。已按此修改（`register_claim`）。

## 阶段 9 · 追加需求："任意网络上都可以使用"

需求从"内网+公网"变成&#x4E86;**"任意网络"**。这不能靠一句话承诺，得落到可测量的工程行为上。

### 9.1 先量化瓶颈

首屏 23 个请求、**810 KB 未压缩**（其中 CodeMirror 单文件 402 KB），  
且服务端**没有 gzip、没有 ETag**——弱网下每次访问都要重传全量。  
这是"任意网络"最大的现实障碍。

### 9.2 做了五件事

| 措施                               | 效果（实测）                                                  |
| -------------------------------- | ------------------------------------------------------- |
| gzip（按 mtime 缓存压缩结果）             | 单文件压到 **26%**：402 KB → 107 KB；全站 810 KB → 约 210 KB      |
| ETag + 条件请求                      | 二次访问 **304，0 字节**                                       |
| 缓存分级                             | `vendor/` 7 天 immutable；业务代码 `no-cache`+ETag（教师改完刷新即生效） |
| 内置 HTTPS（`--tls-cert/--tls-key`） | 无 Nginx 也能让公网用上真机烧录；Cookie 自动加 `Secure`                 |
| Service Worker（网络优先+缓存兜底）        | 断网后**仍能进入应用**继续画图/仿真                                    |

### 9.3 一个必须先想清楚的设计取舍

Service Worker 常见做法是"缓存优先"，但本平台有一条硬需求：**教师随时迭代升级**。  
缓存优先会导致学生长期跑旧版本。所以这里用**网络优先**：  
能连上就拿最新版，连不上才回退缓存。代价是每次请求都要走网络，但有了 ETag/304，  
弱网下的实际传输只有几百字节，可以接受。

### 9.4 发现并修掉的问题

修复要点：

1. 本地记住上次登录身份（**不含任何凭据**），网络错误时以"离线模式"进入应用；

## 阶段 10 · 缺陷修复：点击登录无反应 / 无法跳转

**用户反馈**：输入 teacher 与密码后点"登录"，界面没有任何变化，也没有跳转。

### 复现与定位

先排除环境：`/api/auth/login` 直接请求返回 **200**，教师账号正常 → 问题在前端。

用 Playwright 抓请求，确认复现路径是**密码错误**：

```
POST /api/auth/login → 401 {"error":"账号或密码错误"}
页面 toast: "登录已过期，请重新登录"        ← 完全误导
2.6 秒后 toast 自动消失 → 用户看到的就是"点了没反应"
```

**根因**：`ui/core.js` 的 `api()` 把**所有 401 都当成"会话已失效"**：

```js
if (r.status === 401) { onUnauthorized(); throw new Error('登录已过期，请重新登录'); }
```

登录接口的 401 语义是"账号或密码错误"，却被当成会话过期处理，
既给错提示，又调用了全局"踢回登录页"的逻辑。

### 修复

|  |  |
| --- | --- |
1. **区分两种 401**：`/api/auth/login|register` 的 401 → 抛 `authFailed`，透传服务端文案；
   其它接口的 401 → 仍走 `onUnauthorized()`（这条安全逻辑不能改坏，已用测试锁住）。
2. **可见的内联错误**：不再只靠 2.6 秒消失的 toast，在表单下方常驻红色提示，
   并给出针对性引导（核对输入法 / 教师重置命令 / 学生找教师改密）。
3. **"显示密码"开关**：最常见的失败原因是自动填充了旧密码或打错，能看见才查得出来。
4. **输入归一化**：中文输入法容易打出全角字符（`ｔｅａｃｈｅｒ１２３`），
   肉眼几乎无法分辨，服务端比对必然失败。提交前统一转半角并去掉零宽字符。
5. **忘记密码兜底**：新增 `tools/reset_password.mjs`（`--list` / 重置 / `--must-change`），
   因为内网部署没有邮件找回，没有这个工具一旦忘密码就只能删库。

### 新增测试（`tests/client.test.mjs`，18 项）

这类 bug 在 Node 里不会报、只有浏览器里才出现，所以单列一个**客户端契约**套件：

- 归一化：全角字母/数字/空格、零宽字符、null 安全
- 登录 401 → `authFailed === true`、文案为"账号或密码错误"、**不触发**全局踢出
- 普通接口 401 → 仍然触发踢出（防止修复过头）
- 注册 401 同属凭据尝试；403 透传文案但不标记为凭据失败
- 网络失败 → `offline` 标记（供离线续用逻辑识别）

### 验证

```
错误密码        → 内联红字"账号或密码错误" + 引导，停留在登录页      ✅
全角 teacher１２３ → 正常登录（归一化生效）                          ✅
正确 teacher123  → 正常登录，右上角显示"授课教师"                    ✅
改动输入        → 红色提示自动清除                                  ✅
8 个套件 250 项断言                                                 全通过
```

### 给用户的结论

截图里密码框只有 **8 个点**，而 `teacher123` 是 **10 位**——所以是密码输错了
（或被浏览器自动填充成了旧密码）。现在会遇到明确的红色提示，勾选"显示密码"即可核对；
若确实忘了，用 `node tools/reset_password.mjs teacher 新密码` 一步重置。

## 阶段 11 · 缺陷修复：名单外的学生也能注册

**用户反馈**：不在名单中的学生也可以登录注册。

### 复现：确实有 3 条绕过路径

写脚本逐个试（教师导入 2 人后）：

```
① 名单外学号（学号+班级都填）        → 403  ✅ 拦住了
② 完全不填学号                      → 200  ❌ 注册成功
③ 学号填空串                        → 200  ❌ 注册成功
④ 班级留空 + 借用他人在册学号         → 200  ❌ 注册成功，且同一学号出现两个账号
```

**根因**：校验写成了

```js
if (no && !inRoster && requireRoster) return 403;
```

`no` 为空时整段判断被**短路**——"什么都不填"反而最容易通过。
|  |  |  |
| --- | --- | --- |
另外 `listOnly.some(r => r.studentNo === no && (!className || r.className === className))`
里 `!className` 让班级变成"可省略"，于是借用在册学号 + 班级留空就能过。

### 更隐蔽的第二条路径：设置项被静默关闭

顺着查设置链路，发现两个叠加的问题：

1. `/api/settings/platform` 用 `String(v)` 存值，布尔 `true` 被存成 **`"true"`**，
   而校验比较的是 `'1'` → 不相等 → **名单校验被关闭**。
   也就是说，教师只要点一次"保存设置"（哪怕只改站点名），准入就失效了。
2. 前端 `loadSettings()` 读的是 `s.requireRoster`，而接口返回的是
   `{ llm, platform: {...} }` 嵌套结构 → 永远是 `undefined` → **勾选框始终显示未勾选**，
   教师看到"没勾"，一保存就把 `false` 写进去。

两者叠加，正是"我明明开了名单校验，学生却还能注册"的完整解释。

### 修复

1. 名单校验改为**强制填写**：启用时必须同时提供学号与班级，且两者联合命中名单；
   缺任一 → 400 并说明原因；不命中 → 403。
2. 设置值统一存 `'1'/'0'`，读取用 `settingOn()` 兼容历史 `"true"`；
   启动时自动迁移历史脏值。
3. 前端改读 `platform.*`，接口直接返回布尔值。
4. 补上学号唯一性校验，杜绝"同一学号两个账号"。
5. 新增「允许学生自助注册」开关，把"名单匹配"与"是否开放注册"解耦。

### 顺带修掉一个账号劫持漏洞

既然"认领"能重置密码，而学号本身就是登录名（不是秘密），
那么**任何知道同学学号的人都能把对方密码改掉**。

修复：认领只对 `must_change_pwd = 1`（尚未激活、仍是初始密码）的预建账号开放；
学生自己设过密码后，再"认领"会被拒绝，只能登录或由教师重置。

### 新增测试 `tests/roster.test.mjs`（24 项）

覆盖上述每一条路径：三条绕过、设置项静默关闭（含"只改站点名再保存"的回归）、
开关可逆、账号劫持（认领→再认领→原密码仍有效→攻击者密码无效）、全角输入、学号唯一性。

### 验证

```
9 个套件 274 项断言                                          全通过
界面：两个开关正确回显；只改站点名保存后 requireRoster 仍为 true
名单外注册（全新账号）→ 403 「你的学号未在教师导入的名单中」
浏览器实测：错误提示可见、停留在注册页
```

### 一条工程教训

调试期间我多次"重启服务"其实都因端口被占用而静默失败，旧进程一直服务着，
导致修复后的行为在浏览器里看不到、误以为没改对。**验证服务版本要看接口返回的特征**
（这次是 `/api/info` 的 `requireRoster` 是否已是布尔），而不是只看端口能连上。

## 阶段 13 · 云端链接：先证伪自己的结论，再把它做通

**用户质疑**："为什么不能建立为云端链接？我之前的任务已经做到了。"（附截图：另一门课的
`ac-control-learn.app.workbuddy.host`）

**我错在哪**：上一轮我说"云端不能编译"，其实是**未验证的推测**，并且把"不能编译"
说成了"不能建链接"。链接当然能建。

### 第一次发布：先拿到事实

建了 `cloud/` 瘦身包（1.7MB，排除 280MB Windows 工具链与学生数据）并发布。
用 curl 带上分享码会话调 `/api/compiler/status`：

```
{"sdccUsable":false,"error":"spawn sdcc ENOENT","toolchainDir":"/workspace/toolchain/sdcc/bin"}
```

**结论：沙箱确实没装 SDCC。** 但"没有"不等于"不可能"。

### 第二次：把 Linux 版编译器打包带上去

Debian 官方包里有可用的 Linux 二进制（`sdcc/packihx/sdas8051/sdld`），
按 SDCC 的"可执行文件位置推导数据目录"规则，做成可移植布局：

```
toolchain/sdcc-linux/bin/*            （4.9MB）
toolchain/sdcc-linux/share/sdcc/include   （2.1MB）
toolchain/sdcc-linux/share/sdcc/lib/small{,-stack-auto}  （1.2MB）
```

发布后仍报 ENOENT，但诊断接口暴露了真相：

```
exeExists: true, exeMode: "755", loaders: ["/lib64/ld-linux-x86-64.so.2"]
error: spawn /workspace/toolchain/sdcc-linux/bin/sdcc ENOENT
```

文件在、权限对、链接器在——那 ENOENT 只可能来自 **cwd 不存在**：
`probe()` 把工作目录设成了 `toolchain/sdcc/bin`，而云端只有 `sdcc-linux`。
Node 在 cwd 缺失时抛的就是 ENOENT，极容易误判成"找不到可执行文件"。

修复：`run()` 里 cwd 不存在时回退到 workRoot；PATH 改用"可执行文件所在目录"
（否则 sdcc 找不到它的 sdcpp/sdas8051/sdld）。

### 第三次：发行版头文件本身有 bug

编译能跑了，但卡在 `stc89.h`：

1. `SFR(T2MOD, 0xC9H);` —— Debian 4.2.0 的头文件用了 Keil 风格的 `H` 后缀，4.2 解析器不认；
2. `RCAP2L` 被重复声明 4 次（0xCA/0xCB/0xCC/0xCD 应为 RCAP2L/RCAP2H/TL2/TH2）；
3. `WDT_CONTR` 地址写成 0xC1（官方 4.6.0 是 0xE1）。

这三处是**发行版打包缺陷**，不是我们的用法问题。逐条修正后与官方 4.6.0 的 SFR 表做了
全量 diff，确认完全一致。

### 结果

```
云端 /api/compiler/status : sdccUsable = true, SDCC 4.2.0
云端编译流水灯             : ok=true, 245 字节 HEX, 22ms, 0 错误
浏览器端到端（公网链接）    : 登录 → 载入起始代码(658字) → 编译 → 仿真 327 万机器周期
                          控制台 0 报错，界面显示"编译器：SDCC 就绪"
```

### 教训

1. **不要用推测代替验证**。"云端没有编译器"这句话，成本只有一次发布就能证实或证伪，
   而我先说了结论。
2. **ENOENT 不等于文件不存在**。spawn 的 ENOENT 也可能是 cwd 缺失，必须把
   cwd / PATH / 权限 / 动态链接器分别列为可观测项，而不是猜。
3. 第三方发行包也可能有错（这次是头文件里的三处 SFR 定义），要有与官方版本对拍的意识。

## 阶段 15 · 实验任务 · 过程记录 · 成绩册（按教师确认的规则）

教师确认的四条规则：① 自定义成绩构成 ② 环节内分子项（功能实现/电路设计/报告/调试过程）
③ 总分 60 及格、保留 0 位小数 ④ 用时 = 学生在教师设定的时间窗口内，从打开到提交。

### 数据模型

```
assignments              教师发布的任务（实验、要求、起止时间、发布状态）
assignment_events        学生 open / submit 事件（只记第一次）
grade_scheme             成绩方案（环节 JSON + 子项 JSON + 及格线 + 小数位）
grade_scores             逐格分数（user × stage × item）
```

### 计分实现

```
环节得分 = Σ(子项权重 × 子项分) ÷ Σ子项权重
总评     = Σ(环节权重 × 环节得分) ÷ Σ环节权重
```

两条关键取舍（都已写进测试）：
- **未打分的子项不计入分母**——只打了「功能实现 90」，该环节就是 90，而不是被拉低到 36；
- **整环节未打分则不参与总评**——开学初只评了实验一，学生总评就是实验一的分数。

用时计算会把超出教师设定窗口的部分截断：提前打开从窗口开始算，拖到窗口后才交最多算到窗口结束。

### 界面

- 导航新增「实验任务」「成绩册」（仅教师可见）
- 实验任务：新建/编辑/删除、要求文本、起止时间、完成情况（打开/提交/用时/状态、已提交人数与平均用时）
- 成绩册：环节与子项的增删改权重、及格线与小数位、按环节逐格打分、实时环节分与总评、详情弹窗、CSV 导出
- 学生端：题目详情上方出现任务横幅（要求、窗口、状态、用时），「开始实验」记录时间并跳转 IDE，「提交本次实验」结束计时

## 阶段 17 · 导线跟随元件 · 三极管引脚 · Render 部署指南

### 1. 移动元件时导线不跟随（根因不是"没实现"，是抛异常）

`Schematic.rebindWireEndpoints(movedIds)` 里用的是 `movedIds.has(...)`，
但拖动时调用方传的是**数组**（`drag.ids`），数组没有 `.has` ——
于是只要画布上**存在导线**，一移动元件就抛 TypeError，整个 pointermove 中断，
表现成"导线不跟随、元件也像没拖动"。

修复：
- 入参统一成 Set（`movedIds instanceof Set ? ... : new Set(...)`）；
- 正交化时不再动"已绑在引脚上"的端点（旧代码 `a.y = b.y` 会把导线从引脚上拽走）。

### 2. 顺带把斜线改成直角

两端都绑在引脚、但两个引脚不在同一行/列时，既不能挪端点也不能画斜线。
方案：维护一个 **auto 拐点**（先横后竖），每次重绑时把它同步到最新坐标；
用户亲手拖过该拐点后 `auto=false`，交还给人工。

### 3. 三极管引脚悬空（截图反馈）

引脚定义 `B=(0,2格) C=(5,0格) E=(5,4格)`，旧画法把符号画在盒子正中、引线只画到 X+44，
与真实引脚差 16px，圆点就"飘"在符号外。

修复时踩了第二个坑：E 用 `Y + H` 推坐标（H=60px），而引脚在 dy=4 格 = 48px，
差 12px 导致 E 仍然接不上。最终改为**直接从 `def.pins` 的 dx/dy 取坐标**（未旋转局部坐标，
外层 `<g rot>` 负责旋转），三个引脚全部接通（实测 `allReach: true`）。

### 4. Round 2 的部署地雷：Debian 的 sdcc 4.2.0 头文件有 bug

Docker/Render 镜像用 `apt install sdcc`，而 Debian 4.2.0 自带的 `stc89.h`
正是之前发现的三处错误版本（`0xNNNH` 后缀、RCAP2L 重复 4 次、WDT_CONTR 地址错）。
**直接构建会让所有 `#include <stc89.h>` 的学生程序编译失败。**

处理：
- 把修正版头文件放入 `platform/include/stc89.h`；
- Dockerfile 里用它在构建期**覆盖** `/usr/share/sdcc/include/mcs51/stc89.h`（不依赖 `-I` 顺序，更可靠）；
- 自检从"apt 之后"移到"COPY 之后"，校验的是真正会跑起来的那套文件，
  并特意编译 `T2MOD`、`RCAP2L`（正是出错的那几个寄存器）。

### 5. Render 部署指南

新增 `docs/08-Render部署指南.md`：前置条件 → 推 GitHub → 建 Web Service → 验收 → 磁盘持久化 → 更新 → 排错。
新增 `.gitignore`，实测把 5841 个文件压到 341 个入库，排除 toolchain(294MB)/data(53MB)/cloud(11MB)。

> 关键提醒写进文档：Render **免费实例无持久磁盘**，重启会清空学生数据，

## 阶段 18 · 原理图拖拽卡顿（性能问题定位与修复）

### 现象

拖动元件时明显卡顿，元件越多越严重。

### 定位过程（用数据说话，不猜）

1. 先量「整图重建」本身：327 个节点 / 38KB HTML → **0.53ms/帧**，不是主因；
2. 加临时探针量 `render()` 内部分段（13 个元件的预设电路，单帧 1.28ms）：

   | 阶段 | 每帧 |
   |---|---|
   | 重算电气网络 `sch.refresh()` | 0.09 ms |
   | 生成 SVG 字符串 | 0.15 ms |
   | **替换整个 DOM + 诊断面板** | **0.94 ms** |
   | 网络列表 | 0.09 ms |

3. 结论：**拖拽时每帧都在重建整张图**。单帧 1.3ms 看似不高，但开销与元件数成正比——
   学生画到几十个元件、上百条导线时，每帧要重建数千个 DOM 节点，必然掉帧。

> 顺带发现：用 Playwright 的墙钟测不出差异（每次 `mouse.move` 有 ~8ms 通信开销，
> 淹没了 1ms 级的渲染差异）。改用**页面内合成 `PointerEvent` + `MutationObserver`**
> 才量准：60 次移动 40.4ms（0.67ms/次），整图重建次数 **0**（修复前 40 次移动就重建 39 次）。

### 修复

把渲染拆成两条路径：

- `render()`：整图重绘（重建 SVG + 诊断 + 网络 + 统计），只在非拖拽场景与松手时调用；
- `paintDrag()` / `paintWires()`：拖拽中**只改被拖元件的 `transform` 和相连导线的 `points`**，
  不重建 DOM、不重算净表、不刷新侧栏。

配套改动：
- 拖动开始时缓存被拖元件与其相连导线的 DOM 引用（`drag.els` / `drag.wireIds`）；
- 拐点/整线拖动也只重画该导线与其手柄（`paintWireWithHandles`）；
- `pointerup` 时做一次完整 `sch.refresh() + render()`，清掉临时 transform 并刷新侧栏。
