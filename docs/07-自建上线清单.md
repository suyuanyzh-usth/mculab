# 自建上线清单（不依赖平台发布）

> 背景：平台侧的发布记录已丢失，「设置—数据管理—应用」里已无该应用；
> 会话内的发布能力也不可用。因此改用**自己托管**——这也是正式跑一学期的推荐方式：
> 数据可备份、性能独占、可绑自己的域名和 HTTPS。

两条路，按你有没有服务器选一条。

---

## 路线 A：云主机 + Docker（推荐，常开）

### 0. 准备

- 一台 Linux 云主机（Ubuntu 22.04/24.04，2 核 2G 足够）
- 一个域名（可选但强烈建议：HTTPS 下才能用真机烧录功能）
- 主机安全组放行 **80、443**

### 1. 装 Docker

```bash
curl -fsSL https://get.docker.com | sh
sudo systemctl enable --now docker
```

### 2. 把项目传上去

在**你的 Windows 机器**上执行（Git Bash）：

```bash
cd /c/Users/user/WorkBuddy/2026-09-26-10-47-58

# 只传运行必需的，排除 280MB 的 Windows 版工具链、学生数据和临时文件
tar -czf mculab-release.tgz \
    --exclude='mculab/toolchain' \
    --exclude='mculab/data' \
    --exclude='mculab/cloud' \
    --exclude='mculab/.playwright-cli' \
    --exclude='mculab/node_modules' \
    mculab

scp mculab-release.tgz root@<服务器IP>:/opt/
```

> 注意：`toolchain/sdcc-linux` 会被排除——镜像里用 `apt install sdcc` 安装 Linux 版，
> 不需要打包 Windows 那套。Dockerfile 在构建时会**真的编译一个示例程序并校验 HEX**，
> 工具链有问题会在 `docker build` 阶段直接失败，不会拖到上线后才发现。

### 3. 启动

```bash
cd /opt && tar -xzf mculab-release.tgz && cd mculab

# 强烈建议先改掉默认教师密码
export MCULAB_TEACHER_PWD='你的强密码'

docker compose up -d --build
docker compose ps          # 应显示 healthy
curl http://127.0.0.1:8080/api/health
```

浏览器打开 `http://<服务器IP>:8080`，用 `teacher / 你的密码` 登录。

### 4. 配域名 + HTTPS（Caddy，自动证书）

```bash
sudo apt install -y caddy
sudo tee /etc/caddy/Caddyfile >/dev/null <<'EOF'
mcu.你的域名.com {
    reverse_proxy 127.0.0.1:8080
}
EOF
sudo systemctl reload caddy
```

把域名 A 记录指向服务器 IP 即可，证书自动申请、自动续期。

### 5. 验收

在任意一台电脑上跑（把域名和密码换成你的）：

```bash
node mculab/tools/verify_deploy.mjs "https://mcu.你的域名.com/" 你的密码
```

> 自建环境没有分享码，第一个参数传根地址即可；工具会检查：站点可达 → 教师登录 →
> 六项能力接口 → 编译器。全绿才算上线成功。

### 6. 数据备份与升级

```bash
# 备份（数据在 Docker 命名卷 mculab-data 里）
docker run --rm -v mculab-data:/d -v "$PWD":/b alpine tar czf /b/mculab-data.tgz -C /d .

# 改代码后升级
docker compose up -d --build
```

## 路线 B：本机 + Cloudflare Tunnel（零成本，但电脑要开着）

适合"先让学生用起来、暂时不想买服务器"。

```bash
# 1. 本机启动服务（Windows 双击或命令行）
node server/index.js --port 8080

# 2. 另开一个窗口，建一条隧道（无需注册即可临时使用）
cloudflared tunnel --url http://127.0.0.1:8080
```

命令会打印一个 `https://xxxx.trycloudflare.com` 的公网地址，任何人可访问。

**局限**：电脑关机/休眠即失效；免费隧道地址每次重启都会变；不建议用于正式考核。

## 路线 B 实操记录（2026-11-04 已跑通）

### 关键坑：必须加 `--protocol http2`

首次直接 `cloudflared tunnel --url http://127.0.0.1:8080` 时隧道地址能生成，
但连接始终建不起来。日志里的连通性预检说明原因：

```
UDP Connectivity  region1.v2.argotunnel.com  FAIL  QUIC connection failed
TCP Connectivity  region1.v2.argotunnel.com  FAIL  HTTP/2 connection is blocked
Cloudflare API    api.cloudflare.com:443     PASS
```

**校园网/办公网通常封了 7844 端口**，而 cloudflared 默认走 QUIC(7844)。

加上 `--protocol http2` 后立刻注册成功：

```
Registered tunnel connection ... protocol=http2 location=lax13
```

> 注意：加了这个参数后，预检面板**仍然会报 FAIL**（它逐区测试所有地区），
> 但只要出现 `Registered tunnel connection`，并且公网能访问到，就说明已经通了。
> 以实际访问结果为准，不要被预检的红字误导。

### 实测结果（全部通过）

```
✓ 站点可达并返回平台首页        HTTP 200
✓ 教师账号可登录              角色 teacher
✓ 实验任务 / 成绩册 / 开放性命题 / AI 知识库 / 联网搜索 / 高频错误   6/6 就绪
✓ 判定为新版本
✓ C 编译器可用                SDCC 4.2.0
```

### 一键启动脚本

`deploy/start-public.cmd`：双击即可——自动起服务 + 建隧道 + 打印公网地址。
已内置 `--protocol http2`。

**三条约束（务必让学生知情）**：

1. 这台电脑必须**保持开机且不休眠**，否则链接失效；
2. 每次重启脚本，**公网地址会变**（免费快速隧道不保证固定域名）；
3. 只在实验课时间段开启即可，下课关掉窗口就下线。

## 2026-11-04 12:47 更新：Cloudflare 隧道被阻断，改用 Pinggy

**现象**：原 Cloudflare 隧道运行约 2 小时后失效，公网返回 **HTTP 530**（源站不可达）。
重新建隧道时日志明确报：

```
dial tcp 198.41.192.7:7844: i/o timeout
```

即 **7844 端口已被完全阻断**（上午还能通，说明是动态收紧的策略）。
cloudflared 的 QUIC 与 HTTP/2 两种模式**都要走 7844**，因此这条路在当前网络下不可用。

**替换方案：Pinggy**（走 SSH 的 443 端口，可穿透）

```bash
ssh -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null \
    -p 443 -R0:localhost:8080 a.pinggy.io
```

会打印两个地址，用 `https://xxx.run.pinggy-free.link` 那个。实测：

```
✓ 站点可达 200 ✓ 教师登录 ✓ 六项能力 6/6 ✓ SDCC 可用
```

**代价（必须知道）**：免费隧道 **60 分钟**过期、地址每次变。
`deploy/start-public.cmd` 已按此更新。

> 结论：隧道只适合临时顶用。要长期稳定，请按 `docs/08-Render部署指南.md` 部署到云平台。

## 2026-11-04 13:45 更新：隧道网关域名被 DNS 过滤，改用 IP 直连

Pinggy 隧道运行不到一小时中断，重建时报：

```
ssh: connect to host a.pinggy.io port 443: Network is unreachable
```

排查结论（**不是网络断开**）：

| 检查 | 结果 |
|---|---|
| baidu / github / api.deepseek.com | 全部正常（200/401/200） |
| `nslookup a.pinggy.io`（本机 DNS） | **超时，无结果** |
| `nslookup a.pinggy.io 223.5.5.5`（公共 DNS） | 正常解析出 `139.162.21.36` |
| `serveo.net` / `localhost.run` / `bore.pub` | 本机 DNS 同样解析失败 |
| 本机 IPv6 路由 | 无（ping -6 失败） |

即：**校园网 DNS 把隧道服务域名过滤了**，公共 DNS 能解析、本机解析不出来，
ssh 因此报 "Network is unreachable"。

**解决办法：绕过 DNS，直接连 IP**

```bash
ssh -p 443 -R0:localhost:8080 139.162.21.36    # a.pinggy.io 的 IPv4
```

实测立即分配隧道并可用。`deploy/start-public.cmd` 已内置该 IP（变量 `PINGGY_HOST`）。

> ⚠️ 这是硬编码 IP，服务商更换 IP 时需同步修改。因此它只是权宜之计，
> 不能当作长期方案。

## 2026-11-04 15:16 · 确认免费隧道的硬上限：60 分钟

第三条隧道运行 **1 小时 2 分 36 秒**后被服务端断开，日志明确：

```
===========================
Time exceeded
===========================
Connection to 139.162.21.36 closed by remote host.
```

这不是网络问题，就是 Pinggy 免费版的 **60 分钟连接上限**（建立时已提示
"Your tunnel will expire in 60 minutes"）。

### 对上课的实际影响

| 场景 | 是否够用 |
|---|---|
| 45 分钟的一节课 | ✅ 课前启动、课中分享即可 |
| 两节连堂（90–120 分钟） | ❌ 中途必断，地址会变，需重新发链接 |
| 全天开放给学生自习 | ❌ 完全不可行 |

### 结论

隧道只能作为"临时演示"手段，`deploy/start-public.cmd` 适合课前双击启动。
**正式教学必须部署到云端**（docs/08-Render部署指南.md），否则每 60 分钟就要
重新组织一次链接分发——这对课堂是不可接受的。
